# Contributing Design

Status: APPROVED

Эти правила организации совместной работы установлены при создании baseline. Они не добавляют игровых механик.

- Codex не принимает game-design решения самостоятельно.
- OPEN questions не закрываются без явного CANON UPDATE от владельца дизайна. Молчание, отсутствие значения и пример не являются решением.
- Изменения APPROVED решений фиксируются в [DECISIONS](docs/DECISIONS.md) и [CHANGELOG](docs/CHANGELOG.md) вместе с основанием и затронутыми документами.
- YAML и canonical docs должны быть синхронизированы. Известные расхождения baseline перечисляются в [OPEN_QUESTIONS](docs/OPEN_QUESTIONS.md), а не исправляются по предположению.
- Стабильные ID нельзя молча менять, переименовывать или переиспользовать.
- Новые значения нельзя придумывать для заполнения пробелов. Неполная формула остаётся неполной до решения.
- Используются только статусы APPROVED, DRAFT, OPEN, NOT_STARTED. Версия указывается отдельно.
- Baseline в [docs/source](docs/source/GENOME_GAME_DESIGN_SPEC_v0.1.md) сохраняется; последующие согласованные изменения вносятся в canonical docs с историей решений.
- Правило genome_schema_version из [GENOME_MODEL](docs/genetics/GENOME_MODEL.md), DB §24, применяется к изменениям locus, allele, mutation edge, formula и morphotype threshold. Текущий перенос не меняет schema version.

## CANON UPDATE

Перед изменением игрового правила зафиксировать явное решение владельца дизайна, затронутые OPEN ID, предыдущий и новый смысл, документы и каталоги. Применить именно согласованное изменение, обновить DECISIONS и CHANGELOG, затем проверить ссылки, ID, значения и согласованность YAML/MD. История исходного вопроса и основание решения должны оставаться прослеживаемыми; решённый вопрос получает APPROVED со ссылкой на решение.

При противоречии не выбирать трактовку самостоятельно. Создать вопрос по формату [OPEN_QUESTIONS](docs/OPEN_QUESTIONS.md). Неспроектированный раздел содержит stub и запрет реализации до design approval.

## Проверка документационного изменения

Проверить полноту переноса, ссылки, отсутствующие документы, дубли определений, YAML/MD divergence и скрытые предположения. Организационные правки не должны менять формулы, числа, ID, аллели, локусы или правила. Не начинать реализацию и техническую архитектуру в рамках организации документации.
